# Architecture

## Overview

Task Manager is a monorepo that separates a browser frontend from a REST backend. The initial phase focuses on a small, explicit architecture that is easy to test and later extend with persistent storage.

```text
Browser
  -> LitElement / Web Components
  -> REST over HTTP + JSON
  -> ASP.NET Core 8 Web API
  -> In-memory task store
```

## Frontend boundary

The frontend owns presentation and user interaction only. Custom elements built with LitElement render task lists, task forms, loading indicators, and error messages. Data access is isolated in a service module that uses `fetch` to call the API, so components do not depend on endpoint details.

Planned testing layers:

- Unit tests with Vitest or Web Test Runner for components and the API service.
- E2E tests with Playwright for the full task lifecycle in a real browser.

## Backend boundary

The backend exposes a versionless REST surface under `/api/tasks`. Controllers handle HTTP concerns, while a service abstraction owns CRUD rules. During the first phase the service will read and write an in-memory collection.

The in-memory store is intentionally simple: it validates the task model, assigns identifiers, and keeps state for the lifetime of the process. It will be replaced by Entity Framework Core and SQL Server in the final roadmap phase without changing the public endpoint contract.

## Task model

| Field | Type | Notes |
| --- | --- | --- |
| `id` | `number` | Generated by the backend. |
| `title` | `string` | Required task title. |
| `description` | `string` | Optional details. |
| `completed` | `boolean` | Defaults to `false`. |

## API contract

| Method | Endpoint | Description |
| --- | --- | --- |
| `GET` | `/api/tasks` | Returns all tasks. |
| `POST` | `/api/tasks` | Creates a task and returns the created resource. |
| `PUT` | `/api/tasks/{id}` | Replaces an existing task. |
| `DELETE` | `/api/tasks/{id}` | Removes a task. |

All requests and responses use `application/json`. The frontend treats non-success responses as errors and renders them through a shared error state.

## State and UI behavior

- Collection state lives in a small application store or a top-level component.
- Components receive data through properties and emit custom events for user actions.
- Loading state is shown while requests are in flight.
- Error state is shown when a request fails, with a retry path for list operations.
- Filtering is applied client-side after the list is loaded.

## Gitflow

- `main`: stable, release-ready state.
- `develop`: integration branch for completed work.
- `feature/*`: new functionality.
- `release/*`: release preparation.
- `hotfix/*`: urgent fixes from `main`.

Pull requests target `develop`, except hotfixes, which target both `main` and `develop`.

## Evolution path

1. Add in-memory CRUD to the ASP.NET Core API.
2. Build the LitElement components and static shell.
3. Connect components to the REST API.
4. Add filtering, loading, and error handling.
5. Add unit tests.
6. Add Playwright E2E coverage.
7. Enable GitHub Actions CI.
8. Replace the in-memory store with Entity Framework Core and SQL Server.
